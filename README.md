# buildloop

Is the development loop getting faster or slower, and is CI getting flakier?

Two data sources, trended over time: **GitHub Actions runs** and **local Gradle
builds**. Output is a single static HTML file per project, regenerated by one
command.

```bash
buildloop refresh          # all configured projects
buildloop refresh steady   # just one
```

No server, no daemon, no hosting. No web framework, no build step, no package
manager. The dashboard is a file you open with `file://`, it makes no network
requests, and it works offline.

## Why

GitHub's Actions UI is per-run. It will not show you median workflow duration
by week, failure rate by job, or how much of a run was *queue* time rather than
work — and those are different problems. A run that slowed because the runner
queue was busy needs a different fix from one whose build got slower.

Local Gradle builds are usually not observed at all, despite being where most
of the day goes. Build scans give you one build at a time and no pull-back API.

## Install

Requires Python 3.11+ (macOS ships it) and the [`gh`](https://cli.github.com)
CLI, already authenticated. There is nothing to `pip install` — buildloop is
stdlib-only, on purpose.

```bash
git clone https://github.com/Zeyad-37/buildloop.git
cd buildloop
./bin/buildloop install        # writes ~/.buildloop/config.toml, links the Gradle collector
$EDITOR ~/.buildloop/config.toml
./bin/buildloop refresh --open
```

Put `bin/` on your `PATH` (or symlink `bin/buildloop` into `~/bin`) to drop the
`./`.

The first refresh backfills all available CI history — a few thousand runs,
about a minute — then fetches per-job and per-step detail for the last 90 days,
which takes a handful of minutes. Later refreshes are incremental and near
instant.

### Configuration

`~/.buildloop/config.toml`. Adding a project is three lines:

```toml
[[project]]
name        = "steady"
github_repo = "Zeyad-37/Steady"      # enables the CI collector
gradle_root = "Steady"               # enables the local collector; must match
                                     # rootProject.name in settings.gradle.kts
```

Either key may be omitted; set at least one.

### The Gradle collector

`buildloop install` symlinks `gradle/buildloop.init.gradle.kts` into
`~/.gradle/init.d/`. That covers **every** Gradle build on the machine without
editing a single project's build files — which is also why the script's first
act is to check `rootProject.name` against your config and return immediately
if it isn't tracked.

Two things it is built never to do:

* **Fail a build.** Every collection path is wrapped; any error degrades to a
  debug log and the build proceeds.
* **Cost anything.** Measured on a 60-module KMP project: no detectable
  overhead against run-to-run noise (see `docs/verification.md`).

It is a single `BuildService` that listens for task-completion events and
writes its row when Gradle closes it at the end of the build. The documented
`FlowAction` hook looked like the right answer and silently double-counts every
build from an init script — `docs/verification.md` has the details, because it
is the kind of bug that produces no error at all.

Opt out for one build with `BUILDLOOP_DISABLE=1 ./gradlew …`, or permanently
with `buildloop uninstall`.

## What you get

Two sections that never share an axis, because they measure different
populations — CI is a cold clean checkout on a hosted runner, local is a warm
daemon with a populated cache. Plotting them together produces a comparison
that looks meaningful and is not.

**GitHub Actions**

| Chart | Answers |
|---|---|
| Run duration (median) per workflow | Is CI getting slower? |
| Run duration (p90) per workflow | Is it getting less predictable? |
| Queue time vs execution time | Is it us, or is it GitHub? |
| Failure rate per week | Is CI getting flakier? |
| Failures by job (90d) | *Which* job is the flaky one? |
| Slowest steps (90d) | *Where* inside that job? |

**Local Gradle**

| Chart | Answers |
|---|---|
| Build duration per week | Is my local loop getting slower? |
| Slowest task sets | Which invocations cost me the day? |
| Cache effectiveness | Is the build cache still earning its keep? |
| Configuration-cache hit rate | Am I silently losing the config cache? |

The local charts start empty — there is no way to recover builds that already
happened, so give it a couple of weeks before the local half is interesting.

## How it works

```
  GitHub Actions (N repos)          Local Gradle builds (N projects)
          │  gh api, on demand                │  init script, every build
          ▼                                   ▼
   ci_collector.py                  ~/.buildloop/builds.jsonl
          │                                   │  ingest, on demand
          └──────────────┬────────────────────┘
                         ▼
          ~/.buildloop/buildloop.sqlite
          ci_run / ci_job / ci_step / gradle_build
                         │  generate
                         ▼
          dashboard-<project>.html
```

Four pieces connected by files rather than processes, each independently
replaceable. The Gradle collector is the only always-on part, and all it does
is append a line to a file.

**Why the data lives in `~/.buildloop` and not in a repo:** a repo-local
database gives every `git worktree` checkout its own fragmented history,
splitting the data exactly where it needs to be continuous. One machine, one
store.

**Why the CI backfill is asymmetric:** runs paginate 100 at a time, so all
history costs ~45 requests. Jobs cost one request *per run*, so full-history
jobs would be thousands of requests for detail that only answers
current-state questions ("which job is flaky *now*"). Runs go back forever;
jobs and steps are a rolling 90 days.

### Credentials

There are none. The collector shells out to `gh api` and relies on the token
`gh` already has in your keychain — buildloop never reads, copies, or stores
it. Nothing it captures is sensitive: branch names, workflow/job/step names,
Gradle task paths, durations. Your config, database and generated HTML live in
your home directory and are never committed.

## Uninstall

```bash
buildloop uninstall     # removes the Gradle init script
rm -rf ~/.buildloop     # removes all collected data
```

No consumer repo's build files were ever modified, so builds return to exactly
prior behaviour on the next invocation.

## Non-goals

No server. No auth. No real-time. No alerting — this is for looking at trends
deliberately, not for being paged; threshold alerts belong in CI. No
multi-machine aggregation: local build data is from one laptop, by design.

Portable here means *configurable for your projects*, not *distributable as a
product*. Not planned: Gradle Plugin Portal publishing, a cross-project
comparison UI, a settings UI, any multi-user concept.

## Development

```bash
python3 -m unittest discover -s tests
```

Tests concentrate on the two parsing boundaries where a bug would silently
corrupt history and be hard to notice: GitHub response mapping (duration
arithmetic, re-run handling, pagination boundaries, upsert idempotency) and
JSONL ingest (truncated lines, watermark correctness, re-ingest safety). The
HTML generator is deliberately untested — a visual defect is immediately
obvious, and snapshot-testing hand-rolled SVG costs more than it protects.

The Gradle init script is the exception and gets a manual verification matrix,
because it runs on every local build: see `docs/verification.md`.
